# Ask serving contract — Phases 1 and 2

Phase 1 defines and tests offline aggregate evidence and publication validation.
Phase 2 adds opt-in development publication and consumption, described below.
All routes and independent optimizations default off. Existing Ask continues to
use its governed fact source unless an operator explicitly configures serving.
No production latency or cost improvement follows from offline parity.

## Artifacts and scope

- [Metric inventory](../contracts/ask_serving_metrics.json) enumerates every
  current semantic metric, component formula, unit, direction, aggregation,
  validity rule and phase-composition rule. It is generated by `metric_matrix()`
  and a drift test checks it against the executable semantic catalog. The Phase 1 predicate
  covers points; Phase 2 expansion and default-off routing are described below.
- [Manifest schema](../contracts/ask_serving_publication.schema.json) describes
  candidate publication identity, immutable relation version, semantic/policy
  versions, source snapshot and lineage, coverage, membership, hashes, timestamps
  and freshness policy. It is validated before semantic publication checks.
- `app/agent/serving_contract.py` provides metric-specific summaries and an offline
  adapter preserving the existing aggregate result fields. It is separate from
  game-grain `Evidence`; it cannot certify cohort completeness by itself.
- `app/agent/serving_publication.py` validates candidate manifests and summaries
  against a separately selected, checksummed source snapshot. It performs no I/O to
  BigQuery and never changes a production publication pointer.

## Metric and missingness semantics

Required components share one complete-case appearance set **per metric**.
Missing points therefore do not discard a valid assist observation. Preserve
unrounded component sums, valid and observed membership, missing counts, and the
existing display-rounding behavior. Recorded zeros remain valid. Missing values
(`None` or the existing empty-value representation) remain unknown. Nonfinite or
non-numeric components are rejected as invalid data, not silently omitted.

For counts, totals sum components and averages divide by valid appearances.
Games played counts unique recorded appearances. Ratios and per-36 rates apply
the governed numerator and denominator formulas to the same valid component
sums. A zero denominator or no valid appearances yields unavailable, not zero.
Never infer a DNP or injury from a missing appearance.

Only disjoint phases for the same player, season, and publication can be combined.
Never average rounded phase averages. Preserve game IDs for evidence membership;
these remain private when populated with operational data. A trade does not create
another league-cohort player. Team/date/opponent/venue restrictions are ineligible
for the initial whole-season capability and must not be dropped.

League percentiles and peer distributions can use complete per-player summaries
with the existing qualification, tie and direction policy. Individual game
histograms, trends, and chart series require game-grain detail. Later routes must
preserve claim bindings, complete charts and exact scope; Phase 1 does not replace
renderers or weaken their evidence checks.

## Publication validation and trust boundary

The caller supplies source `Evidence`, the original snapshot, and an independently
selected expected snapshot ID. The validator recomputes the snapshot checksum and
coverage, requires an explicit `cohort_complete: true` attestation, and compares the
reconstructed evidence with the supplied evidence. A changed source cannot reuse
the original checksum. The validator does not authenticate a caller or independently
audit upstream NBA data.
A hash or matching snapshot ID alone does not prove source correctness.

Validation reconstructs expected metric summaries from the trusted source and
compares all rows and membership, not just candidate-reported counts. This prevents
a truncated cohort from becoming valid by recomputing its own hash. Scope records
bind all observed player IDs and appearance membership, date bounds and data-through.
Duplicated/missing summaries, omitted players/phases, altered components, mixed
publication IDs, stale versions and incomplete source cohorts fail validation.
Source corrections require a new source binding and revalidation.

Publication times must be timezone-aware. Version 1 uses `reject_expired` and
requires `source_timestamp <= built_at <= now < expires_at`, with expiry at most
300 seconds after source capture. Rebuilding cannot extend a capture's lifetime.
There is no implicit stale allowance. Eligibility excludes unfinished seasons until
a separate data-through lag policy is reviewed; fresh retrieval alone does not
prove current-season ingestion freshness.
Data-through is the source coverage boundary, not the publication build time.
The source must cover declared season/phase scopes; a future publisher must stage
and validate all relations before atomically moving its pointer. A failed refresh
must retain the prior valid artifact while exposing failure and freshness state.
No atomic publication mechanism is implemented in Phase 1.

A validated candidate exposes a prospective capability predicate taking the entire
`Query` and current time: points total/average, one player and completed season,
supported phases, default qualification, and no additional filters/windows. Expiry
and contract digest are rechecked at use time. `verify_binding` rechecks the complete
summary digest and immutable relation version. These are offline primitives, not
routing approval; a future reader must call binding validation before consumption. Other metrics and shapes
are ineligible even though the offline matrix/parity suite covers their arithmetic.
A capability miss can support a future whole-request fact fallback. Integrity,
permission and malformed-evidence errors must not be hidden behind fallback.
Do not merge partial failed aggregate reads with fresh raw evidence. Planned hybrid
answers must explicitly bind summaries and game detail to the same publication.

Existing fact reads retain row, byte and deadline bounds. Phase 1 leaves fallback
routing unchanged. Identity ambiguity still requires clarification through the
existing resolver; no new alias guessing or identity filtering is introduced.

## Timing and cost inputs

`stage_latency_ms` retains its inclusive semantics for compatibility.
`stage_exclusive_latency_ms` subtracts directly nested synchronous stage time,
including same-name nesting and failed stages. Overview, comparison, split and
snapshot and repeated `Evidence.validate()` validation now have explicit spans. Exclusive stage sums describe
instrumented work, not uninstrumented delivery or an entire end-to-end latency.
These timers assume synchronous nesting; do not interpret overlapping parallel
operations as an additive critical path.

Phase 2 request summaries label
`data_read_coverage=ask_warehouse_reads/2`: governed facts, serving,
repository SQL (including caller-thread governed profile reads), bounded table API
reads, and local ESPN development reads are instrumented. Table metadata and
row-list API attempts record zero on-demand SQL bytes. Other API/transfer charges
are outside this SQL estimate. Governed profile fan-out runs on the caller thread against the shared
request byte budget; it does not occupy the shared page-query pool. Non-Ask
profile calls retain their bounded pool concurrency. This describes
those application paths, not unrelated cloud jobs. Serving cache and reader lock
waits have separate spans. Empty records only establish zero warehouse attempts
within the instrumented request; they do not include publication or hosting.
Request summaries include bounded `data_reads` metadata:

- Warehouse attempts: retrieval success/error, returned row count, processed and
  billed bytes, result-cache hit when reported. Unknown values remain null.
- Evidence-cache accesses: hit/miss, row count, validated source content hash.
  Cache hits do not replay prior warehouse charges.
- At most 64 records are retained per request; `data_reads_dropped` exposes truncation. Exclude incomplete telemetry from complete-cost claims.

No SQL, project/table IDs, job IDs, names, row contents, or provider error bodies
are added to service logs. Source hashes are correlation metadata, not public
source exports. Bounded `serving_shadow` status/error metadata is request-local;
`serving_shadow_dropped` exposes truncation. Shadow reference/read failures retain
the normal fact answer, and points-only candidates use their points capability. Failed reads are recorded even when billed bytes are unknown.
Retrieval success does not imply later semantic validation success; the request
outcome and validation stage must also be inspected.

Model token telemetry includes reported cached-input and reasoning-output tokens.
Unknown details remain null; `token_detail_calls` counts calls reporting each
field, while `usage_reported_calls` gives the usage-reporting denominator. Compare
these with model attempts/failures before estimating cost. Anthropic cache creation/read
fields and OpenRouter token details are included when reported. Anthropic prompt
totals include cache creation and read tokens; pricing must separate their rates.
Missing details, dropped records, and mixed unpriced models make cost unknown.
Reasoning tokens are already part of output tokens. Price conversion belongs in
benchmark reports using applicable rates, not hard-coded into request handling.

The duplicate-rank regression normalizes only two exactly equal raw model
rank queries under a `compare` status, before identity, aggregation or scope
rewrites. Later equality cannot collapse originally distinct rankings. Different metrics, filters, limits or
qualification thresholds still fail the comparison guard. No numerical validation
is relaxed, and this is not a claim about live-provider success rates.

## Validation and later gates

Run the serving, semantic-source/planner, execution, observability, overview,
comparison and split tests, then the existing JSON/SSE endpoint harness. The
`scripts.ask_eval.serving.evaluate` companion uses the existing synthetic frozen
source for catalog/phase parity. Independent numeric fixtures include zero points,
missing components, complete-case shooting ratios and combined phases. Tampering,
expiration and truncated publication tests are distinct from arithmetic parity.
Arithmetic parity uses relative and absolute tolerance 1e-12 for numeric values,
with exact structure/membership. Empty membership is an explicit adapter refusal.

The arithmetic adapter does not reconstruct `run_query` payloads. Even a single-player
summary includes cohort ranks/percentiles, eligibility, exclusion reasons, status
and newest-first membership. Phase 2A requires a cohort-complete publication and an
endpoint adapter preserving all these fields, `no_observations`, provenance, claims
and chart detail. The offline report explicitly states that endpoint payload parity
is not established. No route may be enabled on arithmetic parity alone.

The Phase 1 manifest binds one summary relation. Per-relation inventories, atomic
multi-relation promotion, per-metric validation reports and full payload adapters
remain mandatory integration work before any multi-relation publication.

These checks establish offline contract behavior. They do not establish current
historical warehouse readiness, BigQuery serving query performance, broad model
accuracy, browser rendering performance, or deployed behavior. Historical archive
coverage must be probed independently before the live Phase 2 pilot; a coverage
refusal is not a successful fast answer. Live model/warehouse measurements must identify their exact source, billing mode,
cache state, and sample. Production rollout remains a separate decision.

## Phase 2 development pilot

`serving_runtime.PilotPublication` certifies a publication from a
checksummed source and keeps ordered appearance dates, complete identities and
provenance in a bound metadata envelope. Consumption verifies summary, metadata,
contract and freshness bindings before eligibility checks. It returns the full
`run_query` summary shape, including cohort qualification/ranks/percentiles,
missingness, empty observations and newest-first game membership. Shared cohort
completion lives in `semantics.finish_summaries`; no aggregate rows are wrapped
as game-grain `Evidence`.

`ServingShadow` can be injected into `SemanticWarehouse(serving_shadow=...)` for
local controlled evaluation. Its reference answer is always the normal governed
answer. Candidate outcomes distinguish match, mismatch, ineligible and errors;
the outcome buffer and cooperative request budget are bounded. It is absent by
default. Shadow mode retains the fact preload; serve mode can plan using the bound
complete identity catalog and execute eligible scalar queries before loading facts.
The serving-only arm retains the existing model planner.

`serving_store.DevelopmentPublications` is a POSIX local development store. It
validates before promotion, creates unique artifacts, uses a file lock and expected
generation for atomic pointer replacement, and verifies a bounded artifact read.
Readers require an independently selected expected source ID. Captures are private;
keep the directory outside Git (normally ignored `reports/`). This store retains
old artifacts and has no cleanup scheduler. It is not a BigQuery publisher or a
production multi-relation manifest. Source revalidation on load is preload/build
work, separate from warm compact summary consumption.

Build a local candidate from a fresh captured source with:

```bash
python -m scripts.prepare_ask_serving --snapshot reports/pilot/source.json \
  --expected-source EXPECTED_SOURCE_SHA256 --directory reports/pilot/publications
```

A second promotion must provide `--expected-generation` with the current generation.
The existing 300-second source lifetime still applies. The command makes no warehouse
writes or paid model calls and does not activate the shadow hook.

The existing evaluator companion also exposes `measure_pilot(snapshot, now=...,
repetitions=30)` for paired synthetic full-result timing. It alternates execution
order, reports construction separately and records per-pair parity. This measures
neither endpoint latency nor BigQuery/model cost. Run live measurements only after
source readiness and physical serving publication are verified. A slower synthetic
result is a reason to retain fact routing, not a serving performance claim.


### Consumption performance and integrity

The pilot now loads the semantic contract once per consumption. The same checked
revision supplies the publication fingerprint, capability validation and arithmetic.
No contract approval is cached across requests; a changed contract is checked on
the next consumption. The standalone capability/binding APIs retain their checks.

Summary hashing serializes field values without recursively copying appearance
membership. A regression compares these bytes to the original dataclass serialization.
Metadata integrity hashes the canonical JSON bytes emitted by the builder, before
parsing them. This removes a second encode pass; altered bytes are rejected. Every
consumption still verifies source-bound summary contents, metadata, relation version,
contract digest and expiry. Mutable component changes remain detectable.

The initial paired synthetic calculation benchmark was slower than facts. Profiling
found four YAML contract parses per adapter request versus one in the fact path,
plus unnecessary recursive copies during summary hashing. Removing that repeated
work reduced the 300-player/1,100-appearance adapter median from 30.13 to 12.30 ms,
versus a stable fact median near 14.88 ms (180 full-result pairs). These are offline
calculation measurements, not endpoint latency, BigQuery savings or model-call savings.
Full profiling and follow-up stress results remain in private run artifacts.


## Phase 2 opt-in execution

The application supports the following independent settings, all default off:

| Setting | Meaning |
| --- | --- |
| `ASK_SERVING_MODE=off\|shadow\|serve` | Select reference-only, optional comparison, or eligible serving execution |
| `ASK_SERVING_REFERENCE_PATH` | Private trusted reference JSON; required outside off mode |
| `ASK_SERVING_FAMILIES=points` | Allowlisted families: points, metrics, rankings, detail, rich |
| `ASK_FORMULA_CACHE_ENABLED=false` | Cache validated expression syntax and variable names, never values |
| `ASK_COHORT_CACHE_ENABLED=false` | Reuse a bounded full cohort within one validated publication |
| `ASK_DETERMINISTIC_PLANNING_ENABLED=false` | Exact common-query recognizer `deterministic_common/1` |

The reference pins project, immutable physical table, manifest digest and expected
source snapshot. The project must match application settings. The reader exposes
only allowlisted parameterized SELECTs; publication uses a separate development
class and CLI. `contracts/ask_serving_wire.schema.json` version 3 binds the physical
relation, summary/metric inventory, validation results, metadata and optional detail.
A single atomic `WRITE_EMPTY` load holds all record kinds; no cross-table consistency
assumption is made. Each table expires after one day. Consumption still expires
within 300 seconds of original source capture.

```bash
python -m scripts.publish_ask_serving --snapshot reports/pilot/source.json \
  --expected-source EXPECTED_SOURCE_SHA256 --project PROJECT \
  --dataset ISOLATED_dev --reference-output reports/pilot/reference.json --expanded
```

The dataset must already exist and end in `_dev`. The publisher creates a unique
table, certifies all metric summaries, reads back core and detail, then atomically
replaces a private local reference using a lock and expected previous digest. Failed
publication never advances that reference. Failed candidate tables retain their TTL
for inspection. No refresh scheduler, production pointer or IAM change is provided.

The read-only reader bounds rows (100,000), bytes (100 MB across a request), SDK
and request deadlines, lock waits, and telemetry. Core and detail reads each reserve
at most half the reader ceiling. Unknown billing conservatively reserves the declared
ceiling. Core/detail loading is single-flight and publication scoped. The application reads
a bounded private reference for each complete warehouse operation, pins that
immutable version for the whole governed request, and retains at most two version caches.
Atomic operator promotion is visible without restart. An invalid new reference
fails visibly instead of silently reusing an old version. Every use
checks source binding, contract fingerprint, contents and freshness; cache hits do
not extend approval. Malformed, denied, expired or corrupt publications fail visibly.
An undeclared capability falls back for the whole request without merging partial
results; integrity/permission errors never become successful fact fallback.

## Phase 2 capability expansion

- Counts, games, shooting ratios and per-36 use metric-specific complete-case
  components. Qualification, missingness, ties, direction, exclusions and percentile
  policies share the unchanged governed cohort finisher.
- Rankings retain the complete population, never a top-N-only source. Shooting
  rankings require an explicit supported attempt threshold.
- Player game logs fetch at most 1,000 source-certified appearances with a bound
  player parameter and per-player membership digest. Latest-N/date/phase semantics
  and the league date anchor match facts. A bounded 32-player cache avoids repeated
  warehouse reads. Broader windows and splits use genuine same-publication detail.
- Rich overviews/comparisons retain the existing planner, renderer, required scope,
  optional baseline disclosures, chart and claim checks. They use actual detail when
  the rich family is enabled. Unsupported multi-season capabilities use whole-request
  fact fallback. Aggregate rows never impersonate game-level Evidence.
- Current seasons remain ineligible until a separate data-through lag policy is
  reviewed. Capture freshness does not establish ingestion freshness.

The independent deterministic planner full-matches explicit season/phase count
summaries and qualified leaderboards using governed identity resolution. Ambiguity
clarifies. Extra modifiers, follow-up context, comparisons and unsupported language
retain existing planning. Every recognized Query receives normal semantic validation;
its aggregation provenance is derived by the existing server-owned policy.

## Phase 2 evaluation and costs

The existing `scripts.evaluate_ask` harness accepts `--serving-fixture`,
`--deterministic-common`, `--formula-cache` and `--cohort-cache`. Cassette bindings
include these flags; incompatible replay cannot be reported as matched evidence.
`scripts.ask_eval.serving.measure_endpoint_arms` measures actual JSON/SSE handlers
with caller-owned source/client budgets and retains paired payloads. A TestClient
run is ASGI handler timing, not browser/network latency. The 30 warm/10 app-cache-cold
pilot is exploratory; it is not a p95 commitment or production promotion criterion.

`scripts.ask_eval.costs` requires an injected model/rate/as-of pricebook. Failed
attempts remain in the numerator and successful answers form the denominator.
Model reasoning is not charged twice. Unreported usage/billing or truncated records
leave totals unknown. Capacity billing has zero on-demand marginal charge and requires
separate capacity allocation in full workload totals. Refresh, storage and hosting
must be supplied before calling a workload total complete. Free-tier credits and
actual invoices are distinct from list-rate estimates.

Each query family and planner change needs its own payload, latency and cost evidence
before activation. Fixture success, an explicit older-season pilot, and production
readiness are separate. The absent 2025-26 archive blocks a live last-season pilot;
2024-25 measurements must be labeled explicitly and cannot replace that requirement.


### Request isolation and scope preflight

A governed request pins its first trusted publication selection, including optional
budget scopes. Atomic replacement is picked up by the next request. In-flight readers
retain their pinned version even if the bounded shared cache evicts it; normal freshness
checks still apply. Shadow comparison objects and outcomes are request-local, so
concurrent requests cannot exchange candidates or failures.

Before planning with a publication identity catalog, the reader conservatively requires
coverage for all observed phases of every requested season. Otherwise it retains the
normal full-scope fact resolver, including players absent from the candidate catalog.
A publication without game detail is an undeclared capability, not malformed evidence;
unsupported windows use whole-request fact fallback without attempting a detail read.


## Phase 2 review clarifications

The metric inventory's `routing_enabled: false` records the shipped default,
not an inspection of runtime settings. `pilot_eligible` describes the narrow A2
points contract; expanded families have their own opt-in gates. `detail` jointly
gates exact windows/logs (B3) and filters (B4); `rich` applies only to overview,
comparison and split shapes, not later scalar follow-ups. A points-only gate
retains the narrow A2 predicate even on an expanded publication.

`relation_version` is a logical publication label. Its integrity comes from the
trusted reference's manifest digest and wire `physical_relation` binding, not a
comparison of that label with itself. References declare trusted season/phase
scopes so ineligible requests avoid candidate reads. A request pins one reference
and target generation. Legacy references lacking scopes select facts.

Wire version 3 retains error-free component sum expansions, bound by source
reconstruction and summary digests, so combining phases rounds once and preserves
exact fractional-minute/per-36 ties. Older development publications require
republication. `validation_results` contains the offline source-reconstruction
certificate's source, summary, and contract digests; it does not assert live
validation runs or fabricate per-metric test outcomes. The per-metric inventory
binds certified summary counts and digests to that same manifest.

Core and detail use separate read locks. Valid cached core reads bypass the
cold detail lock. Single-flight waiters remain bounded by the request deadline
(up to 120 seconds), rather than promising nonblocking cold reads. Reference-map
and in-memory cohort locks have separate short waits. Shadow comparisons and
failures appear as bounded, request-local outcome codes.

The all-flags 147-case corpus serves only eligible requests in its complete
fixture variant. Its adversarial variants exercise facts; they do not establish
serving behavior on corrupt or incomplete publications. Dedicated serving tests
cover corruption, expiry, missing references, fallback, scope, and concurrency.
Neither suite establishes live warehouse freshness or deployment health.


### Final review corrections

All timed lock acquisitions release the lock if the deadline checkpoint fails
after acquisition. A timeout cannot strand a process-wide reader, publication,
cohort or version-cache lock. A remaining SQL allowance below 10 MiB fails with
`query_budget_exceeded` before attempting an invalid BigQuery byte ceiling.

Shadow candidates load lazily only when scalar execution actually compares a
result. Overviews, splits, reference and similarity routes do not issue unused
candidate reads. Resolved query family gates apply before candidate selection;
known disabled question requirements also select facts before catalog reads.
Generic reference and similarity routes always retain facts, even with rich enabled.
Points summaries retain the narrow A2 predicate independently of other enabled
families; expiry and binding errors remain visible integrity failures.

Optional shadow execution has a 15-second ceiling with one second reserved for
answer delivery and a two-second negative cache after errors. This is opt-in
measurement work, not a foreground speed promise. Its separate optional ledger
uses at most 50 MB of the remaining 100 MB request cap and reconciles every charge
into the parent ledger, including unknown billed attempts. Failed in-flight jobs
receive best-effort bounded cancellation; cancellation is not proof of zero billing.
Any ordinary candidate exception becomes a bounded shadow error and preserves the
reference answer. No reference payload is mutated by comparison.

Different capture timestamps/job IDs legitimately change source hashes. A shadow
match across those IDs requires identical semantic results under an explicit
source/hash provenance mapping **and** matching publication-bound full-cohort,
per-game identity/scope/metric-input digests for every requested phase and season.
Equal totals or rounded outputs alone are insufficient. Outcomes distinguish
`capture_provenance_differs`, `source_content_differs` and unverified provenance.
Per-season relation mapping and build/expiry metadata retain accurate lineage.

Development promotion requires at least 60 seconds of remaining source lifetime
by default (`--min-remaining-seconds`), checked after readback and immediately
before pointer replacement. At most 20 private prepared receipts retain previous
and candidate references, lifetime and cleanup ownership. A prepared receipt is
not proof of promotion; compare it with the actual current reference. Receipts
never delete warehouse versions; publisher-owned tables retain their one-day TTL.
This adds no refresh scheduler or production publication.
